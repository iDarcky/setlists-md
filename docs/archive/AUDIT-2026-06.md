# Pre-Launch Audit — June 2026

Report-only audit of Setlists.md (`0.10.0` working tree, branch `claude/beautiful-ptolemy-e0h49w`)
covering: code-level security, the live Supabase project, dependencies, build/test/lint
health, and data-integrity/PWA reliability. Native packaging + app-store feasibility is
covered separately in `docs/NATIVE-READINESS.md`.

**No code was changed.** Findings are rated Critical / High / Medium / Low / Info.

## Executive summary

The app is in **good shape to launch as a web PWA for personal (free/sync) use**. There are
no critical security holes: no secrets in the repo, no XSS sinks, RLS is enabled on all 13
production tables, Stripe webhook signatures are verified, edge functions check JWTs, and
security headers (HSTS, X-Frame-Options, nosniff) are deployed.

The risk is concentrated in the **Team/Church tier**: a permissive `team_schedules` policy,
an incomplete `REVOKE` in the security-hardening migration (revoked from `anon` but not
`PUBLIC`, so it did nothing), missing team-membership checks on `team_availability` inserts,
plus the already-known team correctness bugs (read-only bypass, last-write-wins sync). None
of these block a launch where teams are beta/invite-only, but they should be fixed before
promoting the paid team tier.

**Top 5 actions before a public launch:**
1. Fix the `REVOKE ... FROM anon` → `REVOKE ... FROM PUBLIC` issue (S-1).
2. Restrict `team_schedules` writes to admins/leaders or own rows (S-2).
3. Enable leaked-password protection in Supabase Auth (one dashboard toggle) (S-5).
4. Gate all editor entry points with `isTeamReadOnly` (D-1).
5. Commit the live `profiles` (and other dashboard-created) policies into `supabase/migrations/` so the repo is the source of truth (S-4).

### Findings

**S-1 (Medium) — Security-hardening revoke is a no-op: SECURITY DEFINER functions still callable by `anon`.**
`supabase/migrations/20260608_security_hardening.sql:15-21` runs `REVOKE EXECUTE ... FROM anon`,
but Postgres grants `EXECUTE` to `PUBLIC` by default and `anon` inherits it — revoking from
`anon` alone changes nothing. The live security advisor confirms all of
`claim_team_invites`, `get_team_member_profiles`, `get_user_admin_teams`,
`get_user_editable_teams`, `get_user_teams`, `invite_user_to_team`, `is_team_owner` are
still anon-executable, plus three never covered: `handle_new_user`, `log_team_activity`,
`rls_auto_enable` (trigger functions that should not be RPC-callable at all).
Mitigation today: the functions internally check `auth.uid()`, so anon calls return empty
or raise — this is a defense-in-depth gap, not an open door.
*Fix:* `REVOKE EXECUTE ... FROM PUBLIC, anon;` then `GRANT EXECUTE ... TO authenticated;`
for the RPCs; revoke entirely (no grant) for the trigger functions.
Remediation refs: [lint 0028](https://supabase.com/docs/guides/database/database-linter?lint=0028_anon_security_definer_function_executable), [lint 0029](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable).

**S-2 (High, team tier) — Any team member can write any `team_schedules` row.**
`supabase/migrations/20260429_team_schedules.sql:34-55`: INSERT/UPDATE/DELETE policies only
require the caller to be *a member of the team* — not an admin/leader, and not the row's
owner. A regular member can assign people to services, change others' availability
responses, or delete the whole roster for a setlist. Compare `team_songs`/`team_setlists`,
which were hardened to admin-only in `20260521_team_library_admin_only.sql`.
*Fix:* split into "members update own row (`user_id = auth.uid()`)" + "admins manage all".

**S-3 (Medium, team tier) — `team_availability` INSERT doesn't check team membership.**
`supabase/migrations/20260502_team_planning.sql:44-46`: `with check (user_id = auth.uid())`
only. Any signed-in user can insert availability rows into **any** team's calendar
(visible to that team's members). Data pollution, not data exposure.
*Fix:* add the same `team_id in (select public.get_user_teams())` membership check used by
the SELECT policy.

**S-4 (Medium) — Schema drift: live DB and repo migrations have diverged.**
- The live `profiles` policies (`Users read own profile`, `Users update own profile` — seen
  by the advisor) exist in **no file** under `supabase/migrations/`; they were created via
  the dashboard. Same likely applies to `feedback`/`pro_waitlist` shapes.
- The migration table only records migrations from `20260516` onward; everything earlier
  (`20260424`…`20260502`, `20260521`) was applied by hand and is untracked.
A new environment built from the repo would come up **without profiles RLS**.
*Fix:* dump the live policies (`supabase db dump --schema public`) and backfill them as a
baseline migration; apply future SQL only via tracked migrations.

**S-5 (Medium) — Leaked-password protection disabled** (live auth advisor).
HaveIBeenPwned checking is off, so users can register with known-breached passwords.
One-toggle fix in Auth settings. [Remediation](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection).

**S-6 (Low) — `public.feedback` and `public.pro_waitlist` allow unrestricted anonymous INSERT** (`WITH CHECK (true)`).
Intentional for feedback/waitlist, but it's an unauthenticated spam/flooding vector with no
rate limit. *Fix options:* require `authenticated`, or front with an edge function +
rate limit/captcha. [Lint 0024](https://supabase.com/docs/guides/database/database-linter?lint=0024_permissive_rls_policy).

**S-7 (Low) — `set_user_cloud_tokens_updated_at` has a mutable `search_path`** (live advisor).
The other functions were pinned in `20260608_security_hardening.sql`; this trigger was
missed. *Fix:* `alter function ... set search_path = '';`
[Lint 0011](https://supabase.com/docs/guides/database/database-linter?lint=0011_function_search_path_mutable).

**S-8 (Low) — No Content-Security-Policy header.**
`vercel.json` sets the other headers but no CSP. With no user-HTML rendering the practical
XSS risk is low, but a CSP (even report-only to start) is cheap insurance for a launch.

**S-9 (Info) — CORS `Access-Control-Allow-Origin: *` on edge functions**
(`stripe-checkout`, `delete-account`, `cloud-token-exchange`). Acceptable because auth is a
Bearer JWT (not cookies), so cross-site requests can't ride a session. Pinning to the app
origin would still shrink the surface.

## 2. Live Supabase audit (project `biltbdumdwugpepaawku`, read-only)

- **All 13 public tables have RLS enabled** ✅ (`profiles`, `pro_waitlist`, `teams`,
  `team_members`, `team_invites`, `team_songs`, `team_setlists`, `team_schedules`,
  `team_availability`, `user_cloud_tokens`, `feedback`, `shared_setlists`, `team_activity`).
- **Security advisor:** 25 warnings — all folded into findings S-1, S-5, S-6 above.
- **Performance advisor:** 76 items, none urgent at current scale (~12 users):
  - `auth_rls_initplan` ×37 (WARN): nearly every policy calls `auth.uid()` per-row instead
    of `(select auth.uid())`. Fine now; will degrade with table growth. Mechanical fix.
    [Docs](https://supabase.com/docs/guides/database/postgres/row-level-security#call-functions-with-select).
  - `multiple_permissive_policies` ×30 (WARN): overlapping policies (e.g. "Admins can…" +
    "Team editors can…" on `team_setlists`) are each evaluated per query, and they apply to
    the `anon` role because no policy declares `TO authenticated`. Consolidate when touching
    these tables.
  - `unindexed_foreign_keys` ×6, `unused_index` ×3 (INFO): cosmetic at this size.

## 3. Dependency audit

`npm audit`: **3 moderate, 0 high/critical.** All three trace to one chain:
`geist` → `next` → `postcss <8.5.10` (GHSA-qx2v-qp2m-jg93, XSS via unescaped `</style>`).
The app doesn't use Next.js — `geist` (font package) merely declares it — and the vulnerable
postcss stringifier never runs in this app's build or runtime. **Effectively a false
positive**; clears whenever `geist` updates. Do **not** run `npm audit fix --force` (it
downgrades geist to 1.0.0).

`npm outdated`: everything current within semver ranges except three majors held back —
`vite 7→8`, `eslint 9→10`, `@vitejs/plugin-react 5→6`. None are security-driven; upgrade at
leisure. `@supabase/supabase-js` has minor updates available (2.104→2.108).

## 5. Data-integrity & PWA audit

**Solid:** IndexedDB reads are try/catch-wrapped with safe defaults; v1→v2 song migration is
idempotent and tested; tombstones prune after 30 days; an `ErrorBoundary` wraps the app; the
PWA config is healthy (`autoUpdate`, full precache, `cleanupOutdatedCaches`,
`navigateFallback`, sane runtime caching).

**Findings:**

**D-1 (High, team tier) — Read-only team members can still reach the editor.**
`App.jsx` computes `isTeamReadOnly` but not all editor entry points honor it (known issue,
CLAUDE.md). Server-side RLS (`20260521_team_library_admin_only.sql`) blocks the actual
write, so this manifests as members editing locally and **silently losing work on sync** —
a data-loss UX bug rather than a security hole.

**D-2 (High, team tier) — Team sync has no optimistic locking.** Concurrent edits to the
same team song/setlist are last-write-wins with no warning. Either add a version
check-and-swap on push, or document last-write-wins as accepted behavior for v1.

**D-3 (Medium) — Preference cloud-sync push misses ~11 keys.** The push effect's dependency
array in `App.jsx` covers only a subset of `PORTABLE_PREF_KEYS`, so `chartTheme`,
`accentColor`, `sectionColors`, `customSectionTypes`, etc. never sync across devices.

**D-4 (Medium) — Silent storage failure modes.** Load failures return `[]`/`null` without
telling the user; quota is warned at 80% (`getStorageEstimate`) but writes aren't guarded at
100%; IndexedDB saves aren't transactional (a crash mid-`saveSongs` can leave partial
state). Low likelihood, high blast radius — at minimum surface a toast when a save throws.

**D-5 (Medium) — Stale-app/new-schema window.** With `autoUpdate` + stale-while-revalidate,
a user can briefly run old JS against data written by a newer schema. The v2 migration is
forward-only; keep every future schema bump backward-readable for one version (the existing
`schemaVersion` envelope makes this checkable).

**D-6 (Medium) — PDF export is broken on iOS standalone PWA** (known). `window.open` +
`document.write` (`src/pdf/exportSongPdf.js`, `exportSetlistPdf.js`) returns a null handle
in installed PWAs. Tracked in `docs/ROADMAP.md` §7; it's also the #1 webview blocker for
native packaging (see `NATIVE-READINESS.md`).
